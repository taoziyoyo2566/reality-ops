## 1. 目标

效果类似 status.claude.com：持有订阅地址的用户能看到**所有新系统节点**现在是否正常，以及过去每一天、具体从几点到几点出过什么问题。

1. 每个节点一行：当前状态，近 90 天每天一格（正常 / 部分异常 / 故障 / 维护中 / 无数据），90 天可用率；
2. 点开某一天，列出当天每次事件的开始、结束时间（精确到分钟）、影响的连接方式和管理员说明；
3. 管理员在控制台看到同样的内容，外加每次探测的结果与延迟，并可给事件写说明；
4. 页面只显示节点名称，不显示地址、端口、公钥等连接信息。

## 2. 批准时现状

- `[实测]` 2026-09-18：控制台（`spt`，`reality-console`）运行中，4 台节点（`dzire`、`usca`、`legend`、`kagoya`）每 5 分钟上报，
  离线 15 分钟在管理首页提示；这只说明节点上报通道是否正常，不说明用户能否经节点上网。
- `[代码]` 节点登记文件含地址、端口、SNI、公钥与 XHTTP 设置（`dzire`、`usca` 开启 XHTTP），足以生成客户端配置。
- `[代码]` 订阅服务（标准库 HTTP 服务）只提供 `/s/<token>`（浏览器看到用户页，已知客户端得到订阅内容）与 `/s/<token>/<格式>`；
  数据只来自控制台写入的 `catalog.json`、`tokens.json`（D-C1）。
- `[代码]` 应用器按期望状态渲染用户与路由：用户只有 `name`、`uuid`、`short_id`，路由规则来自 SOCKS5 配置，已有 `blocked` 出站；
  改 `short_id` 与路由需要重启 Xray。
- `[实测]` 2026-09-15 `spt` 可用内存约 1.1GB；控制台 web、report 各约 17–39MiB。

## 3. 设计

### 3.1 怎么判断“正常”

- **探测**：`spt` 上的 `status` 服务每 60 秒经每个节点的每种连接方式（Vision；开启时另测 XHTTP）各访问一次检测地址
  （`http://cp.cloudflare.com/generate_204`，期望 204，超时 10 秒）。客户端配置只有经节点的出站，没有直连出站，成功即说明经该节点上网正常。
- **本机自检**：同一轮先从 `spt` 直接访问检测地址；直接访问失败时本轮记为“无数据”，不算节点故障，避免 `spt` 自身断网时误报所有节点故障。
- **事件**：某连接方式连续 3 轮失败，开始一次事件，开始时间记为第一次失败的时间；连续 2 轮成功，事件结束，结束时间记为第一次成功的时间。
  单次失败不开事件。发现故障约需 3 分钟，记录的时间精确到分钟。
- **节点状态**：所有连接方式都在事件中为“故障”，部分连接方式在事件中为“部分异常”，都正常为“正常”。
- **维护中**：管理员在控制台把节点从订阅中隐藏的期间记为维护，维护期间的失败不开事件；状态页照常列出该节点（D-S6）。
- **无数据**：`status` 服务未运行或本机自检失败的时间段，不计入可用率。
- **可用率**：`(有数据的分钟数 − 故障分钟数) ÷ 有数据的分钟数`；维护与部分异常不计为故障，部分异常在每日格中单独着色。
- 节点每 5 分钟的上报继续只在管理页面使用（443 监听、错误日志），不影响状态页。

### 3.2 探测账号（D-S3）

- 每台新系统节点增加一个专用用户 `status-probe`，它的**全部连接都被固定转发到检测地址**（Xray freedom `redirect`），
  不论客户端请求的是什么目标；即使凭据泄漏也只能连到检测地址，不能当作普通代理使用。
  （不按域名放行：嗅探到的域名只用于路由，连接仍发往客户端给出的地址，攻击者可以用允许的域名连到任意 IP。）
- UUID 与 `short_id` 存在 vault（`vault_status_probe_uuid`、`vault_status_probe_short_id`），`edge.yml` 与 `console.yml` 各自读取。
- 期望状态增加 `probe` 段（开关、用户、转发目标），应用器据此加入该用户、一个 freedom 出站（`redirect`）与一条路由规则
  （S3 合同变更，记入其 §10）。转发目标由 `status_check_url` 推导，两边不会各改一处。
- `status-probe` 不写入节点登记文件的用户列表，不参与新旧实例用户比较，不出现在订阅中；控制台收到它的流量上报时不计入用户流量。
- `status_probe_nodes`（`group_vars/all/status.yml`，`edge.yml` 与 `console.yml` 共用）默认等于 `edge_nodes`：
  新系统节点部署时自动纳入状态页，不另外维护名单；首次纳入时该节点 Xray 重启一次（新增 `short_id` 与路由）。
  控制台只探测登记文件中 `status_probe` 为真的节点。

### 3.3 组成与数据流

```text
status（spt，控制台 compose 项目）
  ├─ 读节点登记文件 + 探测凭据 → 生成客户端配置 → 以子进程运行 Xray 客户端（登记变化时重启子进程）
  ├─ 每 60 秒：本机自检 → 经各节点各连接方式访问检测地址 → 写入控制台数据库
  └─ 每轮结束：更新事件与每日汇总 → 写 status.json 到订阅服务数据目录
订阅服务：/s/<token>/status 读 status.json 渲染状态页（token 无效返回 404）；用户页加“节点状态”链接
控制台 web：新增“状态”页；节点详情页显示该节点的事件；事件可写说明（写入后下一轮随 status.json 发布）
```

- `status` 服务使用控制台镜像；镜像以多阶段构建加入节点所用固定 digest 镜像（`edge_xray_image`）中的 Xray 可执行文件。
- `status` 与 `report` 一样写控制台数据库（WAL）；`status.json` 由控制台一侧写入，保持“控制台是订阅数据唯一写入者”（D-C1）。
- `status.json` 只含：生成时间、时区、每个节点的显示名称、当前状态、近 90 天每日汇总、近 90 天事件（开始、结束、类型、影响的连接方式、说明）。

### 3.4 页面

- **用户状态页**（`https://sub.taoziyoyo.com/s/<token>/status`，D-S4）：节点列表与每日格，点开某天看事件；页面每 60 秒自动刷新，不使用脚本；
  页脚说明“检测从服务器侧发起，不能反映你所在网络的情况”。所有持有有效订阅地址的用户看到相同内容（D-S1）。
- **管理状态页**（控制台“状态”）：同样的内容，加每种连接方式最近一次探测的结果、延迟与错误类别，以及 `status` 服务最后一轮的时间。
- **事件说明**：管理员在事件上填写一段文字（例如“机房网络维护”），记录进操作记录。
- **首页“需要注意”**：进行中的故障与部分异常；`status` 服务超过 5 分钟没有完成一轮时提示。
- 时间显示：北京时间（UTC+8），每日格按该时区分日（D-S5）；管理页面其他时间仍为 JST。

### 3.5 数据保存

| 数据 | 内容 | 保留 |
|---|---|---|
| 探测结果 | 每轮、每节点、每种连接方式：时间、成功与否、延迟、错误类别 | 30 天 |
| 事件 | 节点、类型（故障 / 部分异常 / 维护）、影响的连接方式、开始、结束、说明 | 400 天 |
| 每日汇总 | 节点、日期、有数据 / 无数据的秒数（故障、部分异常、维护的时长由事件计算） | 400 天 |

4 台节点约 6 个探测目标，30 天约 26 万行；随控制台每日备份一起备份。

### 3.6 部署形态

- 控制台 compose 项目新增 `status` 服务：非 root（控制台 UID）、只读根文件系统、`cap_drop ALL`、`no-new-privileges`、`init`，
  内存上限 128MiB（Python 与 Xray 子进程合计），只在可出站的网络上，不发布端口；挂载登记目录（只读）、数据库目录、
  订阅服务数据目录与探测凭据目录 `/opt/reality-console/probe`（只读）；健康检查为最近一轮检测不超过 3 个间隔。
- 新增 `group_vars/all/status.yml`：开关、探测节点、探测账号、检测地址、间隔、超时、失败与恢复次数、时区、保留期。
- 订阅服务增加 `/s/<token>/status` 路由与页面，缺少 `status.json` 时显示“暂无状态数据”。

### 3.7 回滚

| 部分 | 回滚 |
|---|---|
| 状态页 | 关闭开关后运行 `console.yml`：停止 `status` 服务并删除 `status.json`；订阅服务的状态页显示“暂无状态数据” |
| 探测账号 | 从 `status_probe_nodes` 移除节点后对该节点运行 `edge.yml`（Xray 重启一次）；全部移除后可删除 vault 中的两项 |
| 数据 | 新增的表不影响 P1 功能；回滚不删除历史数据 |

## 4. 范围与非目标

- **范围**：`console/`（`status` 服务、数据表、管理页面、`status.json` 发布）、`docker/console/`（加入 Xray）、`roles/console_service`、
  `console-remove.yml`、`group_vars/all/status.yml`；应用器与 `roles/xray_edge`（`probe` 段、登记与比较时排除探测用户）、`group_vars/all/edge.yml`；
  `subs/`（状态页路由与渲染）；`tests/console`、`tests/edge`、`tests/subs`；`docs/operations.md`、`docs/project-memory.md`、S3 与 S4 合同 §10。
- **非目标**：从用户所在地区或多个地点探测；通知（邮件、Telegram 等）；延迟曲线与速度测试；旧系统节点；按用户权限过滤可见节点；
  事件订阅与 RSS；手动创建事件。

## 5. 前提、未知与关闭方式

1. **Xray 可执行文件在固定 digest 镜像中的路径与依赖**，能否复制到控制台镜像运行。关闭：本地构建。
2. **检测地址**：`http://cp.cloudflare.com/generate_204` 经节点与直接访问都返回 204。关闭：本地与 `spt` 只读检查；不可用时改用其他 204 地址。
3. **freedom `redirect` 对该用户的所有连接生效**（v26.3.27，Vision 与 XHTTP 都经同一条路由规则）。
   关闭：本地 e2e（检测地址成功；其他地址、其他域名都取不到内容）。
4. **探测流量**：`[实测]` 2026-09-18 本地 e2e：每次探测 11.8KiB（新建 REALITY 连接 + 一次 HTTP），
   即每个探测目标每 30 天约 0.52GB；开启 XHTTP 的节点两个目标合计约 1GB。间隔可在 `status_interval` 调大。
5. **`spt` 内存**：`[实测]` 2026-09-18 本地 e2e：`status` 容器（Python 与 Xray 子进程）52MiB，上限 128MiB。部署前只读检查可用内存。
6. **`spt` 到各节点 443 的可达性**。关闭：部署后第一轮探测结果。

## 6. 验收标准

### 6.1 本地（控制端，无外部写入）

1. **单元测试**：事件判定（2 次失败不开事件、3 次开始、2 次成功结束、开始与结束时间取值）、本机自检失败记为无数据、
   维护期间不开事件、部分异常与故障的区分、按时区分日与可用率、保留期清理、`status.json` 不含地址与凭据、探测用户的流量不计入用户流量。
2. **应用器**：`probe` 段的校验与渲染（用户、`short_id`、freedom 出站与路由规则）；关闭时配置与现在逐字节一致；
   登记文件与用户比较不含探测用户。
3. **订阅服务**：有效 token 返回状态页，无效 token 404，缺少 `status.json` 时显示暂无数据；页面不含脚本与节点地址。
4. **本地 e2e**：本地节点开启探测 → 状态页显示正常；停止节点 Xray 约 3 分钟后显示故障，开始时间为停止后的第一轮；恢复后事件结束；
   只停 XHTTP 时显示部分异常；隐藏节点期间显示维护中；断开本机出站时记为无数据。
5. **部署定义与回归**：compose 加固项齐全；相关 playbook 语法检查；`tests/edge`、`tests/console`、`tests/subs` 全部通过；秘密扫描无 token 与私钥。

### 6.2 上线（各自授权）

1. vault 写入探测凭据后，Ansible 读取正常且不输出其值。
2. 每台节点开启探测账号：Xray 重启一次后，`test` 连接正常，探测账号只能访问检测地址。
3. `spt` 部署后第一轮探测 4 台节点全部正常；`test` 的订阅地址打开状态页，内容与管理状态页一致。
4. 演练：在控制台隐藏、再显示一台节点，状态页出现一段维护记录。

### 6.3 退出条件

§6.1、§6.2 通过；状态页连续运行 24 小时，管理首页没有误报。

## 7. 风险

- **误报**：`spt` 的网络问题或检测地址故障会让所有节点同时失败；以本机自检记为无数据来降低误报，残余风险在事件说明中人工更正。
- **漏报**：只从 `spt` 探测，某个地区单独无法访问某节点的情况看不到；页面上明确说明。
- **探测账号**：一个 UUID 用于所有节点，保存在 vault 与 `spt` 上；全部流量固定转发到检测地址，泄漏的影响限于此，
  发现后轮换（改 vault 后对各节点运行 `edge.yml`）。
- **信息公开范围**：所有订阅用户都能看到全部节点的名称与故障历史；不显示连接信息。
- **流量**：探测流量会出现在节点的出站统计中（§5 第 4 项）。

## 8. 操作者决定

1. **D-S1 可见范围**：只要持有有效订阅地址，不论级别，都能看到所有节点。**2026-09-18 已决定。**
2. **D-S2 颗粒度与判定**：每 60 秒探测一次，连续 3 次失败记为故障、连续 2 次成功记为恢复，经节点真实访问（§3.1）。
   **2026-09-18 已决定：按推荐。**
3. **D-S3 探测账号**：每台新系统节点增加只能连到检测地址的 `status-probe`，凭据存 vault（§3.2）。
   **2026-09-18 已决定：同意**，已记录在 S3 合同 §10。实施时按域名放行改为固定转发（§3.2），约束更严格。
4. **D-S4 状态页地址**：`https://sub.taoziyoyo.com/s/<token>/status`，并在用户页加链接，不另设公开主机名。
   **2026-09-18 已决定：同意**，已记录在 S4 合同 §10。
5. **D-S5 显示时区**：北京时间（UTC+8），每日格按该时区分日。**2026-09-18 已决定。**
6. **D-S6 隐藏中的节点**：在状态页显示为“维护中”。**2026-09-18 已决定。**
