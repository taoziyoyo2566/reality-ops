## 1. 目标

旧系统不再延续，用户不必继续写在仓库文件里。第二阶段让管理员**在网页上管理用户，改完约一分钟内所有节点生效**：

1. 新增、修改、停用、启用、删除用户；设置档位、单独允许 / 禁止的节点、到期日、备注；
2. 新增用户后直接发放订阅地址，不再运行任何命令；批量发放并导出“用户名 + 地址”清单，供迁移时逐个通知；
3. 用户和管理员都能用 Telegram bot 做常用操作；
4. 为以后接入 authentik（OIDC 登录、普通用户查看自己的页面）预留位置，本阶段不接通。

## 3. 设计

### 3.1 用户与档位

- **用户**（控制台数据库为准）：名字、备注、Telegram 账号（可空）、档位、单独允许的节点、单独禁止的节点、到期日（可空）、
  状态（启用 / 停用）、UUID、`short_id`、创建与修改时间，以及预留的 OIDC 身份标识。
- **档位**沿用现有层级：`free < cm < basic < normal < premium`，另有 `all`（全部节点）与特性档位（cmi、netflix、special 等）。
  每台节点有一个档位；用户能用的节点 = 档位不高于自己的节点（`all` 为全部）∪ 单独允许 − 单独禁止（禁止优先）。
  节点档位初始取自 inventory 分组，之后在控制台修改。
- 只有“启用且未到期”的用户会出现在节点上和订阅中；停用不删除订阅地址，重新启用即恢复。

### 3.2 一次性导入与等价校验

- 从 `users/*.yml`、`acl_matrix`、inventory 分组与 `reality_node_users` 导入全部用户、UUID、`short_id` 与节点档位。
- **导入后逐台比较**：控制台按新规则算出的每台节点用户集合，必须与该节点当前登记文件中的集合完全一致；
  有差异时列出、停止切换，由操作者逐条确认（可能来自规则无法表达的例外）。
- 校验通过后 `users/*.yml` 冻结（保留为历史，不再维护）；`generate_user.py` 不再用于新系统。

### 3.3 节点自动生效（节点拉取用户名单）

```text
控制台（spt）  report 服务新增 GET /users：凭节点上报 token，只返回该节点应有的用户（名字、UUID、short_id）与版本号
      ▲
      │ 每 60 秒，经现有 report.taoziyoyo.com 隧道（TLS）
节点 agent（原 reporter 扩展）  版本变化时读取运行中的用户，经 Xray API 增删；结果随上报回传
```

- 节点侧由 reporter 扩展为 agent：同一个容器、同一个 token，新增 Xray 命令行（用于 API 增删用户），不挂 Docker 套接字、不改配置文件。
- **新用户统一使用一个共用 `short_id`**（首次部署时写入各节点配置）：此后增删用户都走 API、不重启 Xray。
  需要未知 `short_id` 的用户不下发，并在控制台标记“需要部署”。
- Xray 重启后，运行中的用户回到配置文件中的集合，agent 在一分钟内补齐差异；`edge.yml` 部署时也从控制台取该节点的用户名单，
  使配置文件与控制台一致。
- 控制台显示每台节点的同步状态：已同步 / 落后（版本号与时间）/ 失败（原因）；节点离线时保持最后一次应用的名单。
- **到期**：到期日一过，控制台不再把该用户列入名单，一分钟内从各在线节点移除；首页提前 N 天提醒。离线节点在恢复连接前仍保留该用户，
  离线期限（TTL）留到路线图 S5。

### 3.4 网页功能

- 用户列表：搜索、按档位 / 状态 / 到期筛选；显示可用节点数、订阅是否发放、最后拉取、本月流量。
- 新增用户：填名字、档位、备注、到期日、例外节点 → 自动生成 UUID → 一键发放订阅地址。
- 编辑、停用 / 启用、删除（删除 = 吊销订阅 + 从节点移除；流量与操作记录保留）。
- 批量发放：勾选多人发放，导出“用户名、地址”清单（只在页面上显示与下载，不写入服务器文件）。
- 节点页：修改节点档位；查看每台节点应有的用户与同步状态。
- 所有写操作沿用第一阶段的表单 token 与来源检查，并记入操作记录。

### 3.5 Telegram bot

- 控制台 compose 项目新增 `bot` 服务：**长轮询，不开放任何端口**，只连 `api.telegram.org`；token 放 vault。
- 绑定：管理员在用户页生成一次性绑定链接（24 小时有效），用户点开即把自己的 Telegram 账号绑到该用户。
- 用户命令：查看订阅地址与二维码、重置地址（二次确认）、本月流量、到期日、节点状态摘要。
- 管理员命令（管理员 Telegram 账号写在配置中）：新增用户、发放地址、停用 / 启用、查询某人。管理员不经 bot 看别人的订阅地址。
- 订阅地址只发给已绑定的本人；Telegram 对话默认不是端到端加密，在用户说明中注明。

### 3.6 认证预留（authentik）

- 认证做成一层中间件：现在固定为“本机管理员”（`console_auth_mode: none`），以后切换为 OIDC（authentik）。
- 页面与操作标注所需角色（管理员 / 用户本人）；操作记录写入执行者；用户表预留 OIDC 身份字段。
- 本阶段不暴露到公网、不接通 OIDC；接通时另立计划（含 Cloudflare 隧道与 authentik 应用配置）。

### 3.7 部署形态与回滚

| 部分 | 回滚 |
|---|---|
| 控制台用户管理 | 保留导入前数据库备份；回滚镜像后，节点保持最后一次应用的名单 |
| 节点 agent | 关闭同步开关后运行 `edge.yml`：恢复为只上报；运行中的用户保持不变 |
| `edge.yml` 的用户来源 | 开关切回 `users/*.yml`（冻结前的版本仍在仓库历史中） |
| bot | 停止 `bot` 服务；绑定关系保留在数据库 |

## 5. 前提、未知与关闭方式

1. **现有 ACL 能否被“档位 + 例外”完整表达**（含 `socks5_only`、`test` 等非层级分组与 `reality_node_users`）。
   关闭：§3.2 等价校验；不能表达的逐条交操作者决定。
2. **共用 `short_id` 与每人 `short_id` 并存**：REALITY 只校验 `short_id` 是否在列表中。关闭：本地 e2e（新旧用户同时连接）。
3. **Xray 命令行在 agent 容器中调用 API**（与应用器相同的 `adu` / `rmu` / `inbounduser`）。关闭：本地 e2e。
4. **report 隧道承载用户名单**：请求频率每节点每分钟一次，响应含 UUID。关闭：本地测量响应大小；鉴权失败返回 401 且不区分原因。
5. **Telegram 出站**：`spt` 能否稳定访问 `api.telegram.org`。关闭：部署前只读检查。

## 7. 风险

- **控制台成为用户的唯一来源**：数据库损坏即丢失用户与凭据。已有每日备份（§14.7）；导入前另做一份。
- **节点 agent 拥有增删用户的能力**：它被攻破时可增删本节点用户（不能改其他配置、不能读私钥）。以只读根文件系统、非 root、
  无 Docker 套接字、只连本机 API 限制。
- **report 服务返回凭据**：每节点只拿到自己的名单，凭本节点 token；某节点 token 泄漏即泄漏该节点的用户 UUID，发现后轮换 token。
- **Telegram**：bot token 泄漏可冒充 bot 发消息，不能读控制台数据；订阅地址经 Telegram 传递，对话非端到端加密。
- **离线节点**：到期、停用、删除在节点恢复连接前不生效（S5 的 TTL 解决）。

## 8. 操作者决定

**2026-09-18 操作者批准本文，以下九项均按推荐做法决定。**

1. **D-P2-1 用户以控制台为准**：`users/*.yml` 导入后冻结，`edge.yml` 的用户来源改为控制台。
2. **D-P2-2 用户属性**：§3.1 的最小集；流量只统计、不做配额。
3. **D-P2-3 档位**：沿用现有层级与特性档位，节点档位可在控制台修改；保留单独允许 / 禁止。
4. **D-P2-4 生效方式**：节点每 60 秒拉取用户名单（§3.3），不再依赖手动运行 `edge.yml`。
5. **D-P2-5 共用 `short_id`**：新用户统一使用，使增删用户不重启 Xray；现有用户保留各自的 `short_id`。
6. **D-P2-6 到期**：到期自动从在线节点移除，并提前 7 天在首页提醒；离线 TTL 留到 S5。
7. **D-P2-7 Telegram bot**：管理员与用户自助都做；订阅地址只发给已绑定的本人。
8. **D-P2-8 取消新旧实例用户集合比较**：旧系统退役后，用户只在新系统维护，比较只会产生噪音。
9. **D-P2-9 认证**：本阶段只做中间件与字段预留，不接通 authentik。
