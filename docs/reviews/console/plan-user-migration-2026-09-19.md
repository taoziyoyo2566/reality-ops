# 用户迁移：让现有用户用上新系统

- 日期：2026-09-19
- 状态：方向已由操作者决定（§5 的 D-M1～D-M3），第一批试点名单待定（D-M4）
- 路线图：[`roadmap-unified-2026-09-18`](../roadmap-unified-2026-09-18.md) §7 S7
- 依赖：控制台第二阶段 2a、2b、2c 已上线（[`plan-console-phase2`](plan-console-phase2-2026-09-18.md)）

## 1. 目标

控制台里的全部用户（2026-09-19 为 34 人）都在新系统上可用：拿到新订阅地址，导入客户端，并在新节点上产生流量。

## 2. 边界

- **旧系统完全不动**：不删除旧用户，不运行旧的 `deploy.yml`，不清理 Gist，也不读取旧监控数据。
  用户迁过来之前，旧地址一直可以用，所以不需要另做回滚。
- 旧系统什么时候整体停用，由操作者另行决定；在此之前不运行 `legacy-remove.yml`。
- **不照搬旧做法**：
  - 地址经 Telegram bot 或控制台网页发放，不用 Gist。
  - 档位和单独允许 / 禁止以控制台为准。它们来自旧档案的一次性导入，之后直接在控制台修改，`users/*.yml` 不再对应。
- 迁移只针对控制台里已有的用户。新用户直接在控制台或 bot 里新增（`/adduser`）。

## 3. 做法

### 3.1 每个用户的阶段

只统计启用且未到期的用户。停用或到期的用户不计入。

| 阶段 | 含义 | 判断依据 |
|---|---|---|
| 未发放 | 还没有新订阅地址 | 控制台没有发放记录 |
| 待导入 | 已发放，还没拉取过 | 订阅服务的访问日志（近 90 天）里没有该用户 |
| 已导入 | 拉取过，但近 30 天在新节点上没有流量 | 有拉取记录，节点上报中没有流量 |
| 使用中 | 近 30 天在新节点上有流量 | 节点上报的流量 |

控制台首页“迁移进度”显示各阶段人数，以及已绑定 Telegram 的人数；点人数进入按该阶段筛选的用户列表。

### 3.2 发地址：以 Telegram 为主

1. 用户列表勾选一批用户（可先筛选“未发放”），点“发放并生成 Telegram 绑定链接”：
   - 没发放的先发放地址，再为每人生成一次性绑定链接；
   - 已经绑定 Telegram 的用户跳过。
2. 链接清单页列出“用户名 → 链接”，并附一段给用户的消息示例。操作者在 Telegram 上把各自的链接私下发给本人。
3. 用户点开链接按“开始”完成绑定，再发 `/sub` 收到地址和二维码，在客户端导入。
4. 链接 24 小时内有效、只能用一次，过期后重新生成。
5. 不用 Telegram 的用户，用“为勾选的用户发放订阅并导出清单”，由操作者把地址私下发给本人。

### 3.3 分批

1. **第一批试点**：2–3 人，名单由操作者指定（D-M4）。确认四件事：能绑定、`/sub` 能取到地址、客户端能导入、之后在新节点有流量。
2. **其余用户**：试点没问题后，一批或分几批发出。

### 3.4 跟踪与收尾

- 每天看首页“迁移进度”。发出后 7 天仍是“待导入”的用户，私下提醒一次。链接过期的，重新生成。
- 迁移结束时仍未使用的用户，由操作者逐个决定：继续等、在控制台停用，或删除（D-M5）。这些操作只影响新系统。

### 3.5 前提

- 7 台新节点（netcup、ams、dcc、jp05、hk01、hk02、jp10）已在控制台“在订阅中显示”。
  2026-09-19 检查时还没有生效，控制台里只有 4 台显示。
- bot 已上线（2c），能正常取得地址。

## 4. 退出条件

每个启用中的用户，要么进入“使用中”，要么已由操作者决定如何处理（§3.4）。旧系统整体停用是另一个决定，不属于本文。

## 5. 操作者决定

1. **D-M1 旧系统不动**（2026-09-19 决定）：迁移只看新系统里的效果，旧系统照常运行，不做按用户的停用。
2. **D-M2 以 Telegram 为主**（2026-09-19 决定）：地址优先通过绑定链接由用户在 bot 里自取，其余用导出清单。
3. **D-M3 迁移进度汇总**（2026-09-19 决定）：控制台首页显示各阶段人数，用户列表可按阶段筛选。
4. **D-M4 第一批试点名单**：待定。
5. **D-M5 长期不迁移的用户**：建议发出 14 天后仍未导入的，操作者私下确认是否还要使用，不再使用的在控制台停用。待定。
